# Arc v8 合成旧数据升级与恢复演练

本设计落实用户在开发分支备份完成后回复“继续推进”所确认的下一项工作：用合成旧数据演练升级与恢复。依据 `docs/operations/v8-local-release-readiness.md` 第 3、5、6 节，沿用现有独立工作树及已批准的子代理、TDD、规格审查后质量/安全审查流程。

## 范围与选择

起点为干净 `f2874d95aa5f8bbe48494aef3768be29c197dcee`，分支 `codex/v8-openrouter-research-beta`。本轮只增加本地测试工具、合成 fixture 和证据文档，不改产品行为、已有迁移、依赖、部署或运行配置。

选择实际非持久化 Miniflare/workerd D1 和 R2，以检查真实本地数据库约束及对象字节。纯 SQLite 更快，但已有相应迁移测试，不能补齐 workerd 恢复证据；生产副本会引入未授权的数据读取与运维。本演练使用完全合成的冻结数据和静止状态逻辑快照，不接入生产副本。

## 归档基线

历史 v7.2 源码 `7ca5b530dfc58f3cbc700b44a7a881a9bd661209` 仅包含 `0000_beta_foundation.sql` 和 `0001_secure_account_linking.sql`，共 20 个用户表。执行前核对归档 SQL 与当前文件的 UTF-8/LF 规范化 SHA256；固定全部七份迁移的哈希，漂移直接失败。只读取这七份已知 SQL，不读取环境文件、真实 Key、用户数据库、日志或实测输出。

先应用 0000–0001，再插入 fixture，最后才应用待执行后缀 0002–0006。不能先创建最终 schema 再插入数据冒充旧库升级。

## 合成数据

所有 20 个旧表至少包含一条有效记录；逐表断言非空。包含两个互相独立的 owner，账户、会话、关联意图、验证记录、学习档案、活动及历史目标、计划和完成的旧任务、完成事件、Proof 根、附件元数据、公开及撤回分享、配额预留/结算或释放、幂等回执、迁移回执及运营/速率/旗标记录。使用显式固定时间、`.invalid` 地址、明显标为 synthetic 的 token/hash 占位值，绝不使用随机生成的真实凭据。

附件实际写入隔离 R2：按 `proof_assets.object_key` 对照每个合成对象，记录字节长度和 SHA256；至少包含不同 owner 的附件，覆盖 Unicode、引号和换行内容。JSON 字段保留原始文本，NULL 与字符串不混淆。

## 演练流程

1. 创建工具内部持有的全新非持久化 D1/R2，不接受外部数据库路径、绑定、环境或生产目标。Miniflare 显式关闭持久化，worker outbound 全部拒绝，资源放在 `finally` 销毁。
2. 建立旧库并填充数据，检查全表覆盖、owner 图、外键与 integrity。捕获静止状态逻辑快照：旧表 schema、列/FK/index 元数据、确定顺序的全量旧行及所有关联 R2 对象字节。
3. 为快照生成校验和。恢复前先验证快照完整性、对象长度/哈希和目标为空；数据或对象被改动、缺失时失败，不能写出“成功”结果。工具只为此合成 fixture 服务，不构建通用备份格式或迁移框架。
4. 在已填充的旧库应用 0002–0006。确认用户表变为 41 个；20 个旧表的每一列、FK、旧索引和行仍保留，允许已批准的新索引。逐项检查旧 owner 关系和附件字节。
5. 在升级库执行旧约束与新的 owner 约束的负例：重复活动目标、重复幂等身份、缺失 owner、跨 owner 的新规划或 Proof 引用。失败前后快照不变，合法新记录可写入。此处是 SQL 约束证据，不冒充完整旧应用或真实 OAuth 验收。
6. 在另一个从快照恢复的库应用部分后缀，然后用明确的无效 SQL 注入失败；确认已经产生部分新 schema，不存在成功收据。不要声称整个生产迁移会自动回滚。
7. 将原始快照恢复到另一个全新库和 R2；比较全部旧 schema/行/对象，证明恢复到旧基线，再应用完整后缀并重复保留检查。源库/源 bucket 不被清空或重用为恢复目标。
8. 所有资源均销毁后，输出只含基线、迁移、计数、哈希及通过状态的摘要，不打印完整 fixture 行、会话值或对象内容。

## 验收与边界

测试必须实际观察 RED 后实现 GREEN；新工具使用 `node:test` 与真实本地存储，断言数据库结果，不用 Mock 代替迁移/恢复。至少覆盖全表保留、正常恢复、中断恢复、迁移漂移拒绝、快照/对象损坏拒绝、非空目标拒绝、约束与失败不留下写入。失败时进程非零，不输出整体通过；不自动重试真实服务。

本地逻辑恢复演练不证明 Cloudflare 原生备份/Time Travel、生产已应用迁移 ledger、部署工具的部分失败/重试、线上保留 artifact、旧应用完整兼容、真实 OAuth 或真实 Research 成功。现有 `migration_runs` 是产品设备迁移回执，不能冒充 D1 schema migration ledger。后续发布门槛必须继续保留这些区别。

实现时验证了 workerd 的检查能力：完整 `PRAGMA integrity_check` 被 SQLITE_AUTH 拒绝。本地健康检查采用受支持的 `PRAGMA quick_check` 加 `PRAGMA foreign_key_check`，并结合完整旧行/索引和约束断言；报告必须准确保留这一范围，不能写成完整 integrity_check 通过。

仍禁止新增真实 Provider 请求、Key 读取、生产 D1/R2/变量/旗标、master 合并、PR、Sites 候选与部署。本轮完成后 root 保存本地交付和恢复检查点；开发分支源码备份沿用已明确确认的公开仓库和范围，不扩大到其他分支或目标。
