# Arc. Public Release Design

## Goal

Turn the validated Arc. experience foundation into a credible public portfolio artifact without expanding the product into live AI, accounts, or server-side persistence.

## Release surface

The release has three coordinated surfaces:

1. **GitHub quality signal.** A single GitHub Actions workflow runs the same unit, lint, production-build, and rendered-HTML checks used locally. Pull requests and `master` pushes use the same Node version declared by the repository.
2. **Repository narrative.** The README becomes the public product page for the codebase: it leads with the visual identity and live experience, explains the core loop and design thesis, documents the active architecture and its deliberately reserved boundaries, and provides exact local commands.
3. **Public product access.** The existing Sites deployment changes from owner-only custom access to public access. This changes the hosting gate, not application behavior or local-data semantics.

## Product and trust boundaries

- Arc. remains a deterministic flagship demo. It does not claim that custom-role content was generated by a live model.
- Learning configuration, progress, and evidence stay in browser storage on the current device.
- Local completion coverage remains distinct from externally verified role readiness.
- Future AI keys must be stored as server-side secrets and must never be embedded in browser code.
- The public release keeps the current Sites URL until the owner provides a custom domain.

## CI design

The workflow uses Ubuntu and Node `22.13.0`, installs with `npm ci`, and runs:

1. `npm run test:unit`
2. `npm run lint`
3. `npm run build`
4. `node --test tests/rendered-html.test.mjs`

It has read-only repository permissions, cancels stale runs for the same ref, and times out after 15 minutes.

## README information architecture

The public README follows the product story rather than the file structure:

1. Brand image, one-sentence promise, CI badge, and live link.
2. The product problem and five-step learning loop.
3. Warm Precision design thesis.
4. Active architecture and technology choices.
5. Honest current boundaries and future integration seams.
6. Local development and verification commands.
7. Focused roadmap toward role intelligence, accounts, and evidence-backed proof.

## Release sequence

Commit the workflow, README, design, and plan on the existing feature branch. Run the full local verification suite, push the branch, wait for GitHub Actions to pass, mark the draft pull request ready, merge it into `master`, and then set the Sites access policy to public. Preserve the feature worktree after the merge until the user requests cleanup.
