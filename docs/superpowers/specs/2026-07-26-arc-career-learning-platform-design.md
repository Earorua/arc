# Arc. 岗位技术栈学习平台设计规格

日期：2026-07-26  
状态：已完成构思，等待书面规格终审  
设计方向：Precision Path / Warm Precision

## 1. 执行摘要

Arc. 是一个面向任意岗位的职业能力操作系统。它把岗位要求转化为可追溯的技术栈地图，再依据用户的现有水平、空闲时间与目标周期生成每天可完成的学习内容。用户的完成记录、项目、代码、笔记与附件持续沉淀为一份可分享的能力证明。

首版同时服务两个目标：

1. 让真实学习者完成“看清目标、执行今天、证明能力”的长期闭环。
2. 让招聘方或潜在客户在三分钟内感受到产品判断、视觉 taste 与完整全栈能力。

产品工作名确定为 `Arc.`。旗舰示例确定为“AI 原生全栈工程师”，同时保留任意岗位生成入口。

## 2. 目标与非目标

### 2.1 产品目标

- 五秒内让访客理解产品价值，并看到唯一主要行动。
- 一分钟内完成无登录设定并得到个性化路线。
- 三分钟内走完“生成路线 → 完成任务 → 更新能力证明”的演示闭环。
- 提供尽可能全面、可追溯、可版本化的岗位技术栈信息。
- 将学习内容压缩成基于真实空闲时间的每日可执行单元。
- 用作品和行为证据构建已有技术栈，而不是只展示主观百分比。
- 即使没有大模型 API Key，也可完整体验旗舰岗位与确定性规划。
- 以克制而有辨识度的视觉与动效证明产品 taste。

### 2.2 首版非目标

- 不绕过限制抓取 LinkedIn 等封闭招聘平台。
- 不建设课程商城、订阅计费、社区、排行榜或即时聊天。
- 不制作原生移动应用、大规模视频课程或直播系统。
- 不建设企业团队管理、导师后台与复杂运营面板。
- 不为了展示技术而拆分微服务、引入区块链或构造无价值的多 Agent 系统。

## 3. 目标用户与核心判断

### 3.1 主要展示对象

首版首先打动招聘方与潜在客户。他们需要迅速看到：

- 清晰的产品定位与用户问题判断。
- 非模板化的视觉表达。
- 可运行的核心闭环，而不是静态概念页。
- 前端、后端、数据、认证、AI、存储与部署的完整能力。
- 对 AI 可信度、失败降级与数据来源的成熟处理。

### 3.2 真实学习者

学习者需要在任何时刻回答三个问题：

1. 我要达到什么岗位能力？
2. 今天有限的时间最应该学什么？
3. 我已经能用什么成果证明能力？

## 4. 产品原则

1. **路线不是目录。** 技术栈必须有依赖关系、优先级、来源、时间和置信度。
2. **每天必须能完成。** 路线要适应真实空闲时间，而不是制造逾期焦虑。
3. **学习必须产出证明。** 每个学习单元遵循“理解 → 练习 → 产出”。
4. **AI 不决定掌握度。** 能力成熟度只能来自完成事件、项目与可验证证据。
5. **一个页面只回答一个问题。** 避免仪表盘卡片墙与过度导航。
6. **先体验、后登录。** 登录只在保存、同步、上传或配置私人模型时出现。
7. **无 Key 仍可用。** AI 是增强层，不是核心闭环的单点故障。

## 5. 核心产品闭环

```text
岗位目标
  → 技术栈地图
  → 个性化阶段路线
  → 今日学习单元
  → 完成与作品证明
  → 能力档案
  → 根据新状态重新排程
```

### 5.1 三分钟旗舰体验

1. 访客选择“AI 原生全栈工程师”。
2. 输入现有水平、每周 7 小时与目标周期。
3. 系统生成 18 周路线并说明生成依据。
4. 访客打开今天的 45 分钟任务。
5. 完成示例产出后，能力档案立即更新。
6. 保存时提示登录，并将访客数据无损合并到账户。

## 6. 信息架构

### 6.1 公开展示层

- `/`：品牌首页。说明价值、展示 Precision Path，并提供“Build my path”主行动。
- `/method`：解释岗位地图、确定性规划与能力证明的方法。
- `/intelligence`：解释来源、更新时间、置信度和 AI 边界。
- `/setup`：四步设定流程；访客无需登录。
- `/profile/:handle`：可分享的公开能力档案。

### 6.2 学习工作区

进入产品后只保留四个一级目的：

- `/today`：当前最值得完成的学习单元。
- `/path`：阶段路线、里程碑与时间调整。
- `/stack`：完整技术栈、依赖、来源与掌握状态。
- `/proof`：项目、代码、附件、笔记与能力档案。

桌面端使用克制的顶部导航；移动端默认进入 Today，并将四个目的压缩为易触达的底部导航。

## 7. 主要页面体验

### 7.1 首页

- 首屏像一张完整海报，不放统计条、Logo 云或浮动仪表盘。
- 品牌 `Arc.` 是最醒目的标识。
- 主标题：`Learn only what moves you forward.`
- 支持文案用一句话说明“岗位技术栈 → 每日行动 → 能力证明”。
- 主行动只有一个：`Build my precise path`。
- 右侧或下方使用纵向章节轨迹：Understand / Build / Prove。

### 7.2 Setup

- 四个连续问题：岗位、现有能力、可用时间、目标周期。
- 视觉上像对话式编辑流程，而非后台表单。
- 每一步只问一个问题，并允许跳过能力自评后使用保守默认值。
- 生成过程显示清晰阶段：规范化岗位、读取知识图谱、补充来源、校验、排程。

### 7.3 Path

- 以纵向编辑式时间轨道展示阶段，而不是甘特图或卡片网格。
- 每个阶段显示目标、周数、关键能力与最终作品。
- 用户调整每周时间或目标日期后，可预览重排差异再确认。

### 7.4 Today

- 首屏突出可用分钟数、任务目标与单一开始按钮。
- 一个学习单元由理解、练习、提交证明三个步骤组成。
- 支持完成、跳过、改天、时间不足与提前完成。
- 任务完成后的主要反馈是成果迁移到 Proof，而不是游戏化撒花。

### 7.5 Stack

- 按基础能力、核心技能、工程实践和加分项分层。
- 支持依赖查看、来源展开、更新时间、置信度和“为什么需要它”。
- 同时显示岗位重要度与个人成熟度，避免将二者混为一个分数。

### 7.6 Proof

- 以技能为索引关联项目、提交、链接、笔记和附件。
- 公开档案只展示用户主动公开的内容。
- 岗位准备度必须可解释，可追溯到具体证据和缺口。

## 8. 视觉系统

### 8.1 视觉命题

`Warm Precision`：像一本被精确编排的未来学习手册。它借鉴 Apple 的克制、节奏与编辑感，但不复刻其具体页面。

### 8.2 色彩

- 象牙白 `#F3EFE6`：主要背景与温暖纸张感。
- 炭黑 `#171715`：核心文本、按钮与深色工作状态。
- 朱砂橙 `#F0643E`：唯一品牌强调色，仅用于当前步骤、进度焦点与关键动作。
- 石灰棕 `#787167`：次级文本。
- 发丝线 `#D7D0C5`：结构分隔。

状态色只在错误、警告和成功语义中出现，不参与品牌装饰。

### 8.3 字体与排版

- 编辑型衬线用于品牌叙事、章节标题和大数字。
- 现代无衬线用于产品操作、标签、表单与正文。
- 中文使用同类气质的系统或开源字体回退，保证加载与可读性。
- 最多两套字体角色；依靠字号、留白和对齐建立层级。

### 8.4 构图与组件

- 默认无卡片；优先使用连续画布、分栏、细线、列表和媒体块。
- 一个视口只有一个主信息和一个主行动。
- 不使用玻璃拟态、渐变堆叠、通用 SaaS 卡片墙和无意义图标。
- 产品界面比品牌首页更安静、更密集，但保持同一排版与色彩系统。

### 8.5 动效

1. 首屏文字按章节顺序进入。
2. 滚动时路线细线生长，当前阶段获得焦点。
3. 完成任务后，成果通过共享布局迁移到 Proof。
4. 所有动效支持 `prefers-reduced-motion`，移动端缩短或取消滚动联动。

## 9. 技术架构

### 9.1 架构原则

采用部署在 Cloudflare Workers 上的边缘端模块化单体。业务模块通过清晰接口隔离，但共享同一代码库与部署单元。首版不拆微服务。

### 9.2 技术栈

- TypeScript、React 19.2、Vite/Vinext、OpenAI Sites、Cloudflare Workers。
- Tailwind CSS 4.x、少量无样式可访问组件原语、Motion for React。
- Cloudflare D1 + Drizzle ORM。
- Cloudflare R2 存储用户主动上传的证明文件。
- Better Auth + Drizzle 处理账户和会话。
- AI SDK 统一多模型供应商；Zod 4 校验输入、模型结构化输出和 API 契约。
- Vitest 覆盖业务逻辑、契约和数据转换。

依赖安装时使用当时最新的兼容稳定版本，并锁定到 lockfile；不使用仅为追新而缺乏稳定性的实验依赖。

### 9.3 业务模块

#### Career Intelligence

- 规范化岗位名称与资历级别。
- 读取旗舰内置知识图谱。
- 通过允许使用的来源适配器、公开 API 与用户粘贴的职位描述补充信息。
- 输出带依赖、重要度、来源、观察时间和置信度的版本化技能图谱。

#### Path Planner

- 根据用户水平、每周时间、目标周期和技能依赖生成阶段路线。
- 排序与时间分配由确定性算法负责。
- AI 只负责语义归纳、内容建议和陌生岗位补全。

#### Daily Engine

- 把阶段路线切分为每日学习单元。
- 处理完成、跳过、时间变化和目标变化。
- 重排前保留历史记录并向用户展示变化摘要。

#### Progress & Proof

- 记录完成事件、项目、链接、笔记和附件。
- 根据证据更新能力成熟度。
- 生成可解释、可分享的公开能力档案。

#### AI Provider Gateway

- 统一 OpenAI、Anthropic、OpenRouter 与兼容接口。
- 管理超时、限流、重试、结构化输出、成本记录与日志脱敏。
- 隔离供应商差异，业务模块不得直接调用具体 SDK。

## 10. 数据模型

主要实体如下：

- `users / accounts / sessions`：认证数据。
- `guest_sessions`：访客状态及账户合并标识。
- `role_profiles`：规范化岗位。
- `role_versions`：岗位地图的版本和生成范围。
- `skills`：技能定义与分类。
- `skill_edges`：前置、包含和相关关系。
- `skill_sources`：来源 URL、标题、观察时间与置信度。
- `learning_plans`：用户路线及约束快照。
- `plan_phases`：阶段目标、顺序与预算时间。
- `learning_units`：每日单元、预计时间和产出要求。
- `completion_events`：完成、跳过、推迟和调整事件。
- `user_skills`：由证据计算的个人成熟度。
- `proof_items`：项目、提交、链接、笔记与 R2 文件引用。
- `ai_provider_configs`：用户可选的加密供应商配置。
- `ai_runs`：模型、用途、耗时、状态和脱敏错误，不保存明文密钥。

所有生成内容必须记录 `createdAt`、生成方式、输入版本和 Schema 版本。

## 11. 核心数据流

```text
岗位输入
  → 岗位规范化
  → 读取内置或缓存图谱
  → 来源适配器补充证据
  → AI 结构化归纳
  → Zod Schema 校验
  → 写入版本化岗位地图
  → 确定性排程
  → 每日学习单元
  → 完成事件与证明
  → 更新个人能力
  → 必要时重排后续路线
```

## 12. AI、来源与可信度

### 12.1 模型配置

- 网站拥有者通过 Sites 服务器环境变量配置默认供应商、模型、API Key 和可选兼容 Base URL。
- 没有默认 Key 时，旗舰岗位使用内置图谱和确定性规划。
- 登录用户可选用自己的供应商配置；密钥只在服务端使用，以服务器主密钥加密后保存。
- 浏览器、客户端状态、分析事件和普通日志都不得出现明文密钥。

### 12.2 结构化契约

- AI 输出必须使用明确的对象或数组 Schema。
- 技能、来源、依赖和学习单元分别使用独立 Schema。
- 输出校验失败时只自动修复一次；再次失败即降级。
- AI 不允许生成无法追溯的虚假来源，也不得直接修改能力成熟度。

### 12.3 来源策略

优先级依次为：

1. 官方文档和官方公开 API。
2. 允许使用的公开数据集与行业报告。
3. 用户粘贴或上传的职位描述。
4. 经过标注的人工整理知识图谱。
5. AI 推断；必须降低置信度并明确标记为推断。

## 13. API 边界

首版内部接口按业务语义组织：

- `POST /api/role-maps/generate`：生成或更新岗位地图。
- `GET /api/role-maps/:id`：读取指定版本及来源。
- `POST /api/plans`：创建学习路线。
- `POST /api/plans/:id/replan`：预览并确认重排。
- `GET /api/today`：读取今日学习单元。
- `POST /api/units/:id/events`：记录完成、跳过或推迟。
- `POST /api/proofs`：创建证明元数据与安全上传流程。
- `GET /api/profiles/:handle`：读取公开能力档案。
- `POST /api/guest/merge`：登录后合并访客数据。

所有写接口必须验证会话、输入 Schema、资源所有权和幂等键。

## 14. 错误处理与降级

- 模型无 Key、超时或限流：回退到缓存或旗舰内置地图。
- 模型输出格式错误：修复一次，仍失败则使用确定性结果。
- 单个来源失败：保留部分结果并显示来源状态，不让整个生成流程失败。
- 重新排程失败：保留原计划与全部历史事件。
- 上传失败：任务完成状态与附件上传解耦，允许稍后补交。
- 乐观更新失败：界面回滚并提供明确重试入口。
- 未知错误：展示用户可执行的恢复操作，同时记录脱敏诊断信息。

## 15. 安全与隐私

- 默认最小化收集个人数据。
- 用户上传内容默认私有，公开档案只展示主动公开项。
- R2 使用受控访问或短期签名 URL，不公开原始桶。
- 用户 BYOK 使用服务器主密钥加密，支持撤销和删除。
- 所有鉴权操作校验资源所有权；访客合并令牌短期有效且只能使用一次。
- 对 AI 请求做速率限制、大小限制与供应商级超时。
- 日志不记录密钥、完整职位隐私内容或上传文件正文。

## 16. 测试与验证

### 16.1 必须自动化的测试

- 排程算法：依赖顺序、时间预算、跳过、提前完成与重新排程。
- 能力计算：没有证据时不得提升，证据移除后结果可重新计算。
- AI 契约：使用固定响应样本验证 Schema、修复与降级。
- 来源合并：去重、时间衰减、冲突处理和置信度规则。
- 访客合并：幂等、所有权、重复登录和冲突处理。
- 数据访问：资源隔离、公开档案过滤与上传权限。
- 组件行为：键盘焦点、错误状态和 reduced-motion 分支。

### 16.2 实施验证

- TypeScript 编译、生产构建和 Vitest 必须通过。
- 数据库迁移必须可重复执行并经过审查。
- 浏览器端到端与视觉 QA 只有在用户后续明确授权时执行；不把未经授权的浏览器检查作为当前默认步骤。

## 17. 首版验收标准

- 首屏只包含一个主要构图、一个主要信息和一个主要行动。
- 新访客无需登录即可走完旗舰闭环。
- 任意岗位入口能返回结构化结果，并明确覆盖范围和置信度。
- 每条岗位技能可查看来源、观察时间和重要度。
- 每日任务根据时间预算生成，并包含可提交的产出。
- 调整时间后，系统预览重排差异且不丢失历史进度。
- 能力档案中的每项成熟度都可追溯到证据。
- 没有模型 Key 时，旗舰岗位与核心交互保持可用。
- 桌面与移动端均可完成核心任务；移动端优先 Today。
- 键盘焦点清晰，动效可关闭，颜色对比满足可访问性要求。
- 架构保持模块化单体，关键业务逻辑与 AI 契约具有自动化测试。

## 18. 建设阶段

### 阶段一：Experience Foundation

- 建立 Arc. 品牌、视觉 tokens、首页和公开说明页。
- 完成无登录设定、Path、Today、Stack、Proof 的可交互旗舰演示。
- 完成响应式布局、核心动效和 reduced-motion。

### 阶段二：Product Intelligence

- 建立 D1 与 Drizzle 数据模型和迁移。
- 建立旗舰岗位图谱、来源模型、AI Gateway 与结构化契约。
- 实现确定性路线规划和每日排程。

### 阶段三：Persistence & Proof

- 实现访客状态、Better Auth、账户合并和跨设备持久化。
- 实现完成事件、能力计算、R2 上传和公开档案。
- 实现 BYOK 加密、撤销与无 Key 降级。

### 阶段四：Production Finish

- 完成错误状态、安全限制、测试和生产构建。
- 生成品牌一致的社交分享图。
- 通过 OpenAI Sites 保存版本并部署。
