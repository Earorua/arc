# Arc. v8 Product Intelligence 设计规格

日期：2026-08-09

状态：用户已批准，进入实施计划阶段

版本基线：Arc. v7.2（GitHub `master` 提交 `7861b8d`）

设计方向：Trusted Intelligence Kernel + OpenRouter Augmentation

## 1. 文档目的

本规格定义 Arc. v8 的产品范围、体验闭环、技术边界、数据结构、AI 策略、失败降级、测试与发布门槛。它建立在已完成的 v7.2 身份认证、账户隔离、设备数据迁移和持久化能力之上，不重新设计登录系统，也不清空或替换现有用户数据。

本规格细化并覆盖主设计规格中与 v8 Product Intelligence 有关的早期假设。尤其是：v8 不提供用户 BYOK；OpenRouter API Key 由 Arc. 站点所有者配置和承担费用，普通用户不输入、查看或管理模型密钥。

本文件只批准设计，不授权直接公开部署。实施必须在后续计划、测试、代码审查和受控 Beta 验收完成后进行。

## 2. 执行摘要

Arc. v8 把当前可交互的学习体验升级为可信、个性化、可持续调整的职业能力系统：

```text
岗位目标
  → 可追溯的岗位技能图谱
  → 优质学习资源
  → 基于能力与时间的完整路线
  → 滚动七日计划
  → 今日可交付成果
  → Proof 验证
  → 有证据的 Stack
  → 按新状态重新规划
```

系统采用“双层岗位模式”：

- `AI-Native Full-Stack Engineer` 是生产质量的 Flagship 岗位，由 Arc. 内置、版本化并人工校验。
- 其他岗位通过 OpenRouter 进行实时 Research Beta。研究结果必须有来源、通过结构化验证并达到可信门槛，才能进入路线生成。

AI 是增强层，不是核心闭环的单点故障。即使 OpenRouter 未配置、超时、余额不足或输出不合格，Flagship 岗位仍须能够完成技能审计、路线生成、每日计划、进度记录、Proof 和 Stack 闭环。

## 3. 已批准的产品决策

1. Flagship-first：首先把 `AI-Native Full-Stack Engineer` 做到生产质量，任意岗位作为受控 Research Beta。
2. 学习资源 English-first；中文界面可以解释资源，但不因语言偏好牺牲资源质量。
3. 资源质量优先于免费与否；必须明确价格状态，并为付费核心资源提供免费替代项。
4. 时间输入采用周一至周日逐日分钟数模板，允许休息日和临时不可用日期。
5. 模型由站点所有者配置；v8 不提供用户 BYOK。
6. 能力入口采用快速技能审计，并允许用户选择性提交 GitHub、项目或其他证据。
7. 每日单元以可交付成果为中心，而不是以“阅读一章”或“观看多少分钟”为中心。
8. 同时展示完整路线和未来七天的详细计划；七日计划滚动更新。
9. 采用“可信情报内核 + AI 增强”，AI 不直接成为事实来源或掌握度裁判。
10. OpenRouter 是 v8 的首个正式 AI Provider；使用固定任务模型策略、受控故障切换和可信本地降级。

## 4. 目标与非目标

### 4.1 产品目标

- 为目标岗位提供尽可能全面、可追溯、可更新的技术栈信息。
- 为每项能力提供高质量学习资源、选择依据、费用信息和替代项。
- 根据用户已有能力和真实每日空闲时间生成可执行计划。
- 通过完成事件和 Proof 更新能力状态，而不是用主观百分比制造进度感。
- 让用户随时回答：目标是什么、今天做什么、已经能用什么成果证明能力。
- 用克制而有辨识度的产品体验展示完整全栈能力、AI 可信设计和产品 taste。
- 保持 v7.2 登录、账户关联、数据隔离和设备迁移行为不回归。

### 4.2 v8 非目标

- 社区、排行榜、即时聊天、导师市场或招聘市场。
- 课程售卖、订阅计费或支付系统。
- 用户自带模型 API Key。
- 原生移动 App、多人协作或企业管理后台。
- 大规模复制、转载或镜像第三方课程内容。
- 用 AI 评分代替可验证证据或人工认证。
- 为展示技术而拆分微服务或构造无价值的多 Agent 系统。

## 5. 核心产品体验

### 5.1 进入路径

访客无需登录即可体验 Flagship 岗位、快速技能审计、本地路线和 Today 示例。登录只在云端保存、跨设备同步、上传 Proof、公开 Profile 或使用站点付费的实时 Research Beta 时出现。

任意岗位的实时研究必须要求已认证账户，并受到账户级、IP 级和全站预算限制。这样既保留“先体验、后登录”，也保护站点所有者的 OpenRouter 额度。

### 5.2 Setup

Setup 每一步只回答一个问题：

1. 选择 Flagship 岗位，或输入一个 Research Beta 岗位。
2. 完成快速技能审计；可选择提交外部证据。
3. 输入周一至周日分别可用的分钟数和休息日。
4. 确认目标水平与计划约束。

生成过程显示真实阶段：规范岗位、读取或研究图谱、验证来源、计算依赖、安排路线、生成七日计划。界面不得把单次不可控的 Loading 伪装成确定进度。

### 5.3 工作区职责

- `Today`：回答“今天有限时间里最值得完成什么”。
- `Path`：回答“完整路线是什么、当前在哪里、为什么这样排序”。
- `Stack`：回答“已经形成了哪些有证据的能力、还缺什么”。
- `Proof`：回答“提交了什么、如何验证、如何迭代和公开”。
- `Profile`：把用户主动公开的能力与成果组织为可分享的职业叙事。

每个页面只保留一个主要动作。AI 不以悬浮聊天机器人出现，而以 `Research this role`、`Generate my path`、`Rebalance this week` 和 `Review this proof` 等边界明确的产品动作出现。

## 6. 可信岗位情报与学习资源

### 6.1 双层岗位模式

Flagship 岗位使用版本化的内置 Role Blueprint。它在 OpenRouter 关闭时也必须完整可用，并作为所有算法、测试和 UI 的黄金样本。

Research Beta 接受任意岗位名称，但不会承诺所有岗位都立即达到生产质量。它输出研究状态、来源覆盖、置信度和缺口；证据不足时进入 `Needs review`，不得静默发布路线。

### 6.2 Role Blueprint

每个可发布岗位蓝图至少包含：

- 规范岗位名、目标水平、适用范围和排除范围。
- 技能定义、类别、岗位重要性和掌握标准。
- 技能之间的前置、包含和相关关系。
- 对应岗位职责与代表性可交付成果。
- 主要资源、替代资源、费用、语言、内容类型、难度和预计时长。
- 来源 URL、来源等级、观察时间、最后核验时间和可信度。
- 蓝图版本、生成方式、Schema 版本和变更摘要。

### 6.3 来源优先级

资源按以下顺序选择：

1. 官方文档、技术标准、规范和原始课程。
2. 大学、技术公司及公认教育平台的高质量材料。
3. 有明确作者、实践背景和更新时间的工程内容。
4. 社区内容只作为补充，不承担核心知识教学。

系统只保存资源元数据、短摘要、技能映射和原始链接，不镜像完整文章或付费课程。付费核心资源必须提供免费替代项；价格不明时显示 `Price unverified`，不得猜测。

### 6.4 情报流水线

```text
岗位输入
  → 名称与水平归一化
  → OpenRouter 联网研究
  → 提取技能、依赖、职责与资源
  → JSON Schema 验证
  → 来源去重、分级与时效评分
  → 领域规则验证
  → Role Blueprint Draft
  → Ready / Needs review / Failed
```

AI 输出首先是 Draft。任何没有可访问来源、技能映射或明确范围的结果都不能进入可信蓝图。网页文本始终视为不可信输入，不能修改系统规则、模型策略或触发外部副作用。

## 7. 路线与每日学习引擎

### 7.1 规划输入与输出

规划输入包括岗位蓝图、技能审计、可选证据、逐日时间预算、休息日、历史完成事件和已有 Proof。

规划输出分为两层：

- 完整路线：全部阶段、技能依赖、里程碑和预计完成区间。
- 滚动七日计划：未来七天的具体 Daily Units，只详细生成足以执行的近期内容。

完成历史和已验证证据不可被重排覆盖。计划变更必须创建新版本，并显示变更原因、移动内容和预计完成时间变化。

### 7.2 确定性规划边界

技能依赖顺序、分钟预算、休息日、已完成内容保护和状态转换由确定性领域规则负责。OpenRouter 可以建议内容、解释排序和补全 Research Beta，但不能绕过依赖或超出用户当日预算。

规划器必须保证：

- 不安排尚未满足前置条件的核心任务。
- 每日计划总时长不超过该日可用分钟数；无法完整容纳时拆分或顺延。
- 休息日不安排强制任务。
- 已完成单元不重新变为未完成。
- 重新规划保留所有历史事件并产生可读差异。

### 7.3 Daily Unit 契约

每个 Daily Unit 必须包含：

- 今天要获得的具体能力。
- 为什么现在学习它。
- 一个主要资源和必要的替代项。
- 分时执行步骤。
- 一个动手构建任务。
- 明确的完成标准。
- 所需 Proof 及其验证 Rubric。
- 预计耗时和对应技能。

“学习数据库基础”不是合格单元；“设计并提交一个包含索引、约束和可验证查询结果的数据模型”才是合格单元。

### 7.4 动态调整

跳过、延期、提前完成、实际耗时偏差、空闲时间变化、Proof 通过或未通过、技能依赖更新和资源失效都可以触发重新规划。

重新规划失败时继续使用上一份有效计划。系统不得先覆盖旧计划再尝试恢复。

## 8. Progress、Proof 与 Stack

### 8.1 能力状态

```text
Not assessed → Planned → Learning → Demonstrated → Verified
```

- `Demonstrated` 表示用户已提交满足基本完成标准的证据。
- `Verified` 绝不能仅由模型评价授予。v8 只有在该单元定义了可由服务器执行的确定性验证器且验证通过时才授予；其他证据最高保持 `Demonstrated`。
- 未来若增加人工认证，必须作为独立、可追溯的审核事件设计，不在 v8 中伪装实现。

### 8.2 Proof 类型与版本

Proof 可以是 GitHub 仓库、Commit、Pull Request、已部署网页或 API、文档、截图、测试报告、代码文件、其他构建产物和简短复盘。

Proof 必须关联 Daily Unit、技能和完成标准。提交后保持不可变；修订创建新版本，并保留原始提交、差异、验证结果、AI 反馈、时间和关联技能。

### 8.3 验证流水线

```text
提交 Proof
  → 验证身份、所有权和输入
  → 保存不可变元数据与私有文件
  → 执行链接、文件和领域规则检查
  → OpenRouter 按 Rubric 提供辅助反馈
  → 写入验证事件
  → 更新能力状态
  → 必要时触发重新规划
```

AI 反馈必须标记为辅助评审，并显示模型运行状态和置信边界。验证不可用时 Proof 保存为 `Pending review`，不能错误提升技能。

### 8.4 Stack 与公开 Profile

Stack 是证据支持的能力账本，不是技术标签墙。每项技术显示状态、岗位重要性、完成单元、最强 Proof、最近使用时间和下一步建议，并能反向进入路线与证据。

Proof 和上传文件默认私有。用户必须明确选择后才能发布到 Profile；公开页面只读取被允许的版本，不暴露私人学习记录、AI 原始反馈或私有文件地址。

## 9. 技术架构

### 9.1 总体结构

```text
React 用户界面
  ↓
Server API 与认证/授权边界
  ↓
Role Intelligence / Resource Registry / Path / Planning / Proof / Stack
  ↓
D1 结构化数据 + R2 私有文件
  ↓
Provider-neutral AI Gateway
  ↓
OpenRouter Adapter
```

v8 继续使用当前 Cloudflare 边缘端模块化单体。业务模块共享仓库和部署单元，但通过类型化接口和独立领域契约隔离。前端不得直接访问 D1、R2 或 OpenRouter。

### 9.2 领域模块

- `Role Intelligence`：岗位归一化、技能图谱、来源与版本。
- `Resource Registry`：资源元数据、质量、费用、有效性和技能映射。
- `Path Engine`：完整阶段路线和依赖排序。
- `Planning Engine`：滚动七日计划、事件处理和重排差异。
- `Proof Engine`：证据、版本、确定性验证和 AI 辅助反馈。
- `Stack Ledger`：从事件与证据投影用户能力状态。
- `AI Gateway`：任务模型策略、结构化契约、预算、日志、超时和降级。

各模块必须可以在不读取实现内部的情况下通过其输入、输出和错误契约被理解与测试。具体 Provider SDK 只能出现在 AI Gateway 的适配层。

## 10. OpenRouter 接入设计

### 10.1 接入方式

OpenRouter 是 v8 首个正式 Provider。实现优先使用其稳定的 OpenAI-compatible Chat Completions 接口；如果未来采用 OpenRouter Responses API Beta，必须作为单独适配能力并通过相同领域契约，不能让业务代码依赖 Beta 响应形状。

实时研究使用 OpenRouter 当前推荐的 `openrouter:web_search` Server Tool，不使用已弃用的 `:online` 或旧 Web Search Plugin。结构化结果使用严格 JSON Schema，并要求路由到支持请求参数的 Provider。

参考：

- [OpenRouter Quickstart](https://openrouter.ai/docs/quickstart)
- [Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs)
- [Web Search Server Tool](https://openrouter.ai/docs/guides/features/server-tools/web-search)
- [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection)

### 10.2 固定任务模型策略

部署配置必须为以下任务提供明确模型 ID：

- Research：岗位与资源联网研究。
- Planning：路线与 Daily Unit 内容建议。
- Review：Proof Rubric 辅助评审。
- Economy：低风险修订、摘要或格式修复。

模型 ID 不写死在产品文案中，也不允许浏览器覆盖。每次 AI Run 记录最终模型、Provider、用途和配置版本，以确保结果可追溯。启用前每个模型必须通过对应任务的固定质量样本；未配置或未通过时该任务保持关闭并使用降级路径。

OpenRouter 可以在同一模型的合格 Provider 之间受控故障切换，但必须要求所需参数并保持数据策略。不得使用无法解释模型选择的全自动路由作为 v8 默认生产策略。

### 10.3 服务端配置

至少包含以下服务端变量或等价配置：

- `ARC_AI_ENABLED`
- `OPENROUTER_API_KEY`
- `ARC_AI_MODEL_RESEARCH`
- `ARC_AI_MODEL_PLANNING`
- `ARC_AI_MODEL_REVIEW`
- `ARC_AI_MODEL_ECONOMY`
- 单次、每日和每月成本限制

只有在总开关、密钥、任务模型和预算均有效时才允许 live AI。密钥只能存在于 Sites 服务端 Secret；不得进入客户端 Bundle、普通环境变量展示、数据库明文、日志、错误响应或 Git 历史。

### 10.4 数据与路由策略

- Provider Routing 强制使用 `data_collection: "deny"`。
- 任务模型与 Provider 支持时优先使用 ZDR。只有被明确标记为“ZDR 必需”的任务才把 ZDR 当作硬门槛；这类任务没有合格端点时必须降级，不能静默放宽要求。
- 发送给模型的数据遵循最小化原则；研究任务不需要用户身份，Proof 评审只发送完成 Rubric 所必需的内容。
- 原始上传文件不自动发送给模型；需要模型分析时必须经过类型、大小、权限和内容边界检查。
- 全部调用有超时、有限重试、并发限制、账户级限流和全站预算断路器。

### 10.5 输出验证与降级

AI 输出必须依次通过：传输解析、JSON Schema、领域规则、来源验证和安全过滤。格式修复最多一次；再次失败即降级。

降级行为：

- Flagship 使用内置蓝图和确定性规划继续工作。
- Research Beta 保留研究草稿并进入 `Needs review` 或 `Failed`，不生成正式路线。
- Proof 保持 `Pending review`，不改变能力状态。
- UI 保留上一份有效结果，并给出可执行的重试或继续使用本地模式入口。

## 11. 数据模型

v8 在现有 D1 结构上增量扩展。最终表名可在实施计划中按现有约定调整，但领域实体和关系不得丢失：

- `role_blueprints`：岗位范围、状态、当前发布版本。
- `role_blueprint_versions`：不可变图谱版本、来源覆盖和变更摘要。
- `skills`：技能定义、分类和掌握标准。
- `skill_edges`：前置、包含和相关关系。
- `resources`：URL、语言、价格、类型、时长、来源等级和核验时间。
- `resource_skill_links`：资源与技能、阶段和用途映射。
- `research_runs`：岗位研究状态、阶段、错误和恢复信息。
- `learning_paths` / `path_versions`：用户路线及约束快照。
- `daily_units`：结果目标、步骤、预算、资源、Proof 要求和 Rubric。
- `plan_versions`：滚动七日计划版本与变更原因。
- `progress_events`：完成、跳过、延期、耗时和调整事件。
- `proof_items` / `proof_versions`：证据元数据、不可变修订和 R2 引用。
- `proof_reviews`：确定性检查、AI 辅助反馈和最终状态。
- `user_skills`：由事件与证据投影的当前技能状态。
- `ai_runs`：任务、模型、Provider、Token、成本、耗时、状态和 Schema 版本。

R2 只保存用户上传文件；D1 保存所有者、类型、大小、校验值、访问状态和对象键。所有私有读取都必须经过服务器身份和所有权检查，不暴露可预测的公开对象地址。

所有生成和规划记录必须包含 `createdAt`、生成方式、输入版本、Schema 版本和幂等键。

## 12. 状态、并发与恢复

Research Run 使用：

```text
Queued → Researching → Validating → Ready / Needs review / Failed
```

各阶段状态写入 D1。用户关闭页面后状态不会丢失；重新进入时可以读取、恢复或安全重试。若部署环境不保证长时间后台执行，工作流必须拆成可恢复的有界阶段，而不能假装浏览器关闭后仍一定持续运行。

路线、计划、Proof 和研究写操作使用版本号与幂等键。重复点击、网络重试或回调重放不能创建重复完成事件、重复 Proof 或重复扣费调用。并发写入冲突必须返回可恢复的冲突状态，不采用最后写入静默覆盖。

## 13. 错误与安全边界

- 所有写 API 验证会话、输入 Schema、资源所有权和幂等键。
- Research Beta、AI Review 和其他付费调用要求认证，并限制账户、IP、时间窗口和全站预算。
- 外部 URL 只允许 `https` 或受控 `http`，并阻止私有网络、环回地址、非网页协议和无限重定向，避免 SSRF。
- 上传验证类型、大小、文件名和所有权；原始文件默认私有。
- 外部文本和模型文本在展示前按上下文安全编码，防止 XSS。
- 日志不记录密钥、完整私有 Proof、原始上传正文或不必要的个人信息。
- 未知错误返回脱敏 Request ID 和明确恢复操作；内部诊断保留错误类别，不向客户端泄露堆栈与密钥。
- 数据迁移采用可重复执行的增量迁移；v7 数据必须在迁移预演、备份和回滚路径确认后才能应用生产。

## 14. 视觉与交互语言

v8 采用 `Editorial Precision`：温暖纸张白、近黑文字、克制珊瑚色强调；高对比衬线标题、清晰无衬线正文和等宽元数据。依靠排版、留白、细分隔线和严格网格建立层级。

不得使用泛滥渐变、玻璃拟态、厚重阴影、通用 SaaS 卡片墙和无意义图标。状态与 AI 可信度优先用明确文字和层级表达，不堆叠彩色徽章。

动效只用于层级变化、路线重排、Proof 状态推进和技能进入 Stack。动效短促、可中断，并尊重 `prefers-reduced-motion`。

移动端保留易触达的底部主导航并默认突出 Today；桌面端为 Path、Stack 和 Proof 提供更宽的编辑式视图。核心路径按 WCAG 2.2 AA 的键盘、焦点、语义和对比要求设计。

公开 Product Notes 可以克制展示 Arc. 的架构、可信 AI 决策和版本演进，但不能让技术展示压过学习任务。

## 15. 测试策略

### 15.1 领域单元测试

- 技能依赖排序、循环检测和先修约束。
- 逐日分钟预算、休息日、拆分、延期和重新规划。
- 已完成事件保护与计划差异生成。
- Proof 状态与 Stack 投影；无证据不得提升。
- AI 预算、断路器、有限重试和幂等行为。

### 15.2 AI 契约与质量测试

- 使用固定合法、缺字段、恶意指令、虚假来源和超长响应样本验证 Schema 与降级。
- 使用固定岗位黄金样本验证技能覆盖、来源完整性、资源质量、依赖合理性和 Daily Unit 可执行性。
- 模型或 Provider 变更必须重新运行对应任务质量集，并记录配置版本。
- 测试默认使用 Stub/Fake；常规测试套件不得产生真实 OpenRouter 费用。

### 15.3 集成与安全测试

- Better Auth 身份、账户隔离、Guest Merge 和双 Provider 登录回归。
- D1 增量迁移、版本冲突、事务边界和重复请求。
- R2 私有文件所有权、补偿流程和公开版本过滤。
- 越权访问、Prompt Injection、XSS、SSRF、恶意文件和频率滥用。
- OpenRouter 超时、429、余额不足、无效 JSON、无可用 Provider 和预算耗尽。

### 15.4 端到端验收

```text
注册或登录
  → 技能审计
  → 生成路线
  → 查看 Today
  → 完成任务
  → 提交 Proof
  → 验证能力
  → Stack 更新
  → 退出并重新登录
  → 数据保持一致
```

还必须分别验证：Guest Flagship 无 AI 闭环、已认证 Research Beta、手机端核心流程、桌面端完整路线，以及 OpenRouter 关闭后的降级体验。

## 16. 发布门槛

只有满足以下条件才允许公开部署 v8：

- v7.2 Google、GitHub 登录、退出、账户关联、账户隔离和迁移行为无回归。
- 数据库迁移完成预演，现有用户、进度和 Proof 完整保留，并具备明确回滚路径。
- Flagship 岗位在 `ARC_AI_ENABLED=false` 时仍可完成核心闭环。
- Research Beta 的失败、低置信度和无来源结果不会进入正式路线。
- OpenRouter 密钥边界、预算、限流、日志和数据路由策略生效。
- 自动化测试、TypeScript、Lint、生产构建和健康检查全部通过。
- 手机与桌面核心路径完成人工验收。
- 无阻断级安全、可访问性或数据完整性问题。

v8 先作为受控 Beta 部署。只有用户完成关键体验验收并明确批准，才能替换当前公开版本。

## 17. v8 完成定义

v8 必须交付：

- 生产质量的 Flagship 岗位蓝图与优质学习资源。
- 快速技能审计和可选证据输入。
- 周一至周日逐日时间配置。
- 完整路线与滚动七日计划。
- Outcome-driven Daily Units。
- 进度事件与可解释重新规划。
- Proof 提交、版本、验证和反馈。
- 有证据支持的 Stack 与选择性公开 Profile。
- OpenRouter 固定任务模型策略和实时岗位 Research Beta。
- 无 AI、AI 失败和预算耗尽时的可信降级。
- 与上述范围匹配的自动化、集成、安全、端到端和人工验收证据。

任何仅完成页面、Mock 数据或 AI 演示而未打通上述闭环的版本，都不能标记为 v8 完成。

## 18. 与早期主规格的差异

- 保留 Cloudflare 边缘端模块化单体、D1、R2、Better Auth、类型化 Schema 和确定性规划原则。
- 将早期“多 Provider/BYOK”范围缩小为“Provider-neutral Gateway + 站点所有者配置 OpenRouter”。
- 将任意岗位从无条件生成改为带可信门槛的 Research Beta。
- 将资源策略从一般来源列表提升为带价格、语言、替代项、核验时间和版权边界的 Resource Registry。
- 将计划明确为“完整路线 + 滚动七日详细计划”。
- 将技能状态明确为 Proof 驱动，并禁止 AI 单独授予 `Verified`。
- 将 OpenRouter 预算、防滥用、数据路由和服务端 Secret 边界列为发布门槛。

## 19. 后续流程

1. 用户终审本书面规格。
2. 规格批准后，单独编写可执行实施计划；此时仍不自动公开部署。
3. 从最新 `master` 创建独立 `codex/arc-v8-*` 实施分支或 worktree。
4. 按测试驱动方式分阶段实现，逐阶段验证并提交。
5. 完成代码审查、受控 Beta 部署和用户人工验收。
6. 只有获得明确批准后，才发布为新的公开版本。
