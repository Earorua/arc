# Planning observation binding audit — 2026-11-07

Status: offline, read-only product audit; ignored local probes/memo only. Baseline supplied by parent: `f9bd733`; product implementation `67a1af3`; independent evaluator `5d9fa48`. No source, frozen fixture, scorer, history record, or proof asset was edited. No real provider was instantiated or called, no network request was made, no remote migration/deploy/push/commit occurred. All SQLite databases used `:memory:`. This is **not** a fixed 14-case integration run, a product qualification, or a new Gate pass.

## Decision

The frozen v2.1 planning projection cannot currently be a faithful, complete product observation contract. The dominant problems are incompatible state semantics, an insufficient native before-state, and some missing product action paths. They cannot be repaired by adding case-derived revision counters, audit IDs, proof digests, task content, or rejection state in a collector.

Keep the frozen evaluator and its constructed-control pass records unchanged. Author a separately versioned native observation binding/reference, independently review its before states and declarative invariants, then implement a collector against that contract. Do not change product fact confirmation to mutate a plan just to satisfy an invented unified revision.

A distinct **P1 product gap** was verified: changes to adopted material context can be lost when they do not change order/dates. `proposeMaterialReplanResponse` returns `no-change`; `recordNoChange` writes only a mutation receipt, and enabled goal links remain on the original context. This affects explicit learning-focus adoption/withdrawal and same-job primary-JD replacement in the bounded scenes below. The proposed context exists, but no current adopted-context transition occurs. This is separate from the frozen fixture's artificial bookkeeping.

## Verified bounded findings

1. **Native before-state schema mismatch:** `planningTargetSchema` rejects the frozen `budget.weeks=2` as `targetWeeks` (minimum 4). Native `artifactUrl` rejects `local:contract-test-record`. Translating both `primary-jd` and `secondary-jd` to native `slot:jd` rejects with “Too many jd selections”. These checks use actual product schemas, not scorer predicates.
2. **Focus choice with no reordering:** start with an adopted primary SQL-must JD, a confirmed SQL supplement, actual plan generation, two actual completions, and a `ProofService.create` submission. Change `learningIntents` absent→present or present→absent through `MaterialContextService.create`, then request a material replan. Both return `no-change`; complete planning workspace and Proof workspace remain equal, enabled links still point to initial `context-8`. New choice only exists in the new preview/snapshot. No after-state was seeded.
3. **Existing-plan self assessment:** changing only SQL `conceptual`→`guided` in the context audit returns `no-change` with an explicit unapplied-change message; the actual workspace audit is unchanged. Search finds `adoptMaterialSelfAssessments` only in its definition and tests, not a product caller. There is no self-adoption document endpoint and no self-adoption planning event. The pure function accepts individual guided/independent and rejects batch independent, but does not persist an existing workspace update or audit trail.
4. **Deletion:** actual `deleteDocument` on the adopted supplement returns `cleanup-pending`, increments the document revision, revokes dependent selections/contexts/proposals, clears sensitive context payloads, and disables that document's links. The complete planning and Proof workspaces remain unchanged. This is correct preservation, not evidence that planning revision should increment. Whole-document `detachAdoptedMaterial` is different: it records `material_usage_changed` and increments the planning revision while disabling a specific adopted link.
5. **Unresolved review point:** a legitimate, source-bound unresolved `conflicting-requirement` review point was seeded as BEFORE state into a real saved draft. Actual confirmation rejects `invalid-content`; no confirmation row is created. Product review points are not the fixture's `{skillId,status,alternatives}` conflict ledger.
6. **Stale context:** create a goal-bound material context at native revision 2, append a real third completion (revision 3), then propose from the old context. The service rejects `CONFLICT` and all captured state remains unchanged. This tests stale context-to-proposal fencing, not the frozen `apply-preview` action against an already pending plan.
7. **Same-job no-change replacement:** initial A is SQL must; a resume and supplement are also adopted. Complete the two SQL units. Replace A with C=React must in the same goal's selection. Preview correctly changes React rank 5→0, SQL 0→3; remaining TypeScript/Web prerequisites already force the same order, so service returns `no-change`. The old A context remains adopted. The first probe's “must propose” assumption was wrong for this native before state; the independent observer records the true result. This also demonstrates why a generated full path cannot be silently substituted for the frozen five-task before state.
8. **Successful explicit acceptance:** separate scene C=observability must has a ready unfinished task and produces a real proposal. Planning revisions are 2 before, 3 staged, 4 accepted. Sidecar contains `input_revision=2`, `proposal_revision=3`, old active base-plan ID, candidate-plan ID, native context ID/fingerprint. During staging, active path/plan and adopted A links remain unchanged. Acceptance switches links to C and preserves resume/supplement. Sorted complete path-unit objects (IDs/templates/checkpoints/dependencies/minutes), completed events, audit, and all retained prior DailyUnit objects are preserved. Raw output includes the candidate/current path/plan and contexts. No claim is made that this one scene proves all task-content projections or all 14 frozen cases.

## Legal before-state and identity rules

1. Pin native product/source versions and store a complete `nativeBefore` hash. The current `{before,action}` fixture hash does not bind missing weekday allocations, native task content, proof review chain, confirmation IDs, context IDs, sidecars, actual requests, or dependency graphs. Adding these silently under the existing hash would change the experiment.
2. Seed only owner-scoped in-memory records. Prefer real create/review/confirm/select/generate/complete/Proof services to establish before state. A preconfirmed grounded extraction can be independently constructed for a planning-only fixture, but must carry valid source/version/review provenance and be labeled synthetic before input; it is not model-quality evidence. Unsupported manual skillLabels must not be inserted by the action adapter.
3. Do not substitute the helper's full generated path for the frozen minimal five-task set, nor project a subset of a larger path. The actual probes deliberately use separate full native before states and explicitly do not submit results to the frozen scorer. If a five-task native snapshot is desired, independently author all native path/plan/DailyUnit/history details and prove service/repository legality; do not merely pass a weak shape parser and claim full generator reachability.
4. Use actual complete-task events to establish completed state. Native completions target the currently actionable primary DailyUnit and can move the rolling seven-day view. Use a separate real Proof ledger submission/validation path. Verified proof requires an actual successful deterministic validator event, not an arbitrary timestamp or a synthetic all-`a` digest.
5. Store a bijective alias manifest: fixture document→native document/version/text/confirmation; item→native item/preview reference; logical task→path-unit ID and template/version/checkpoint; goal/role; context; candidate plan; proof ID/version. Resolve IDs from actual receipts and persisted keys. Do not infer IDs from desired outcomes, collapse distinct IDs, shift revision values, replace digests, or invent audit IDs.
6. Native source APIs legally permit one primary JD, one resume, and up to three supplements. A secondary JD must be explicitly represented as supplemental input from the start, with that classification preserved as test-input provenance. It cannot be a second native JD secretly renamed only in the observer.
7. Protected data should compare complete native objects/rows, not booleans, selected excerpts, task counts, or digest-only claims. Preserve full native objects in bounded evidence, with object digests for integrity. Distinguish set identity/content equality from the intentionally mutable task ordering and placement.

## Minimum collector and separately versioned contract work

- Define a new native observation envelope with source commit, scenario/input/binding manifest digests, setup trace, action trace, raw API outcomes/errors, before/after read receipts, and independent native revision domains. Captured after data must come from service reloads and scoped SQL; it cannot copy the frozen before and overlay `constraints.expectedChanges`.
- Capture full planning workspace (including source context reference), actual planning repository representation where the browser strips the material fingerprint, Proof workspace and its rows, document/review/confirmation records relevant to the test, selection/context/dependency/proposal/usage/link rows, and mutation receipts. Keep context/plan preview phases distinct. Render bounded summaries from these captures.
- Freeze a native fixture version with complete legal inputs and expected invariant changes independently authored/reviewed. Preserve old v2.1 constructed-control results and label the new version separately. The scorer remains deterministic and must not call the product planner/mapper to generate expected after values. Observation collection may invoke real product operations; expected truth must remain independent.
- Use native action outcomes and stable native identifiers. If a human-friendly reason such as stale-context is derived, retain actual code and supporting mismatched fence values; do not globally translate any `CONFLICT` into that reason.
- Add comparator coverage for retained complete task content, checkpoint/template identity, complete dependency graph/minutes, historical completed DailyUnits/events, Proof versions/reviews/projections, exact remaining set/order, daily budget/timezone/exceptions, active-versus-proposed context, and no reappearance of removed choices after explicit adoption. New native limits must fit complete data without dropping records.
- Keep self adoption component tests explicitly component-scoped until a real UI/service persistence path is defined. The existing-plan reorder limitation from approved design §5.5/§8.6 is a reason to preserve task sets, not permission to silently mutate audit or claim helper return values are persisted.

## P1 follow-up boundary for product repair

The actionable product issue is the lack of a successful explicit context-only adoption when material semantics change but order/dates do not. A future authorized repair should provide an explicit, reviewable transition that atomically adopts the current bound material context/choices while preserving existing tasks, completed records and Proof. It must validate the same owner, goal/workspace/base/revision, selected versions, confirmations, source, context fingerprint/token and expiry fences, and must invalidate obsolete attempts. Decide how this appears in history and whether a new native metadata event is required before implementation.

Do **not** repair this by making `createMaterialContext` or fact confirmation silently apply changes. Do **not** force an arbitrary reorder to obtain a candidate. Do **not** treat whole-document detachment as individual-focus withdrawal. Self-audit replacement remains a separate behavior/design decision.
